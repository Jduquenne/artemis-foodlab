# API (as consumed by the front)

Contracts of `meals-planning-api` that the front relies on, captured from the API session and real payloads. The API repo is authoritative; this file is the front's reference. Front-side behaviour lives in `docs/spec-*.md`.

## Working with the API session

A separate Claude Code session owns `meals-planning-api` (sibling repo). Collaboration is a **relay driven by the owner**:

- Write the question as a self-contained, precise, copy-pastable prompt, and **always introduce it explicitly** with a short label such as "Prompt to paste into the API session:" — never post a bare block.
- Do not guess the shape of a complex endpoint (nested resources, polymorphism) without a concrete example; wait for the **real payloads captured in prod or dev**. For simple endpoints following a confirmed pattern, a reasonable assumption + empirical verification is acceptable.
- A decision that affects the other side's data model (unique constraint, opening a route to a role) is raised to the owner as a **product decision**.
- Even a confirmed text contract deserves empirical verification, especially when the endpoint is only local: run the API locally (`npm run dev` in the API repo), create a throwaway account (`NEW_USER_EMAIL=… NEW_USER_PASSWORD=… npx tsx scripts/createUser.ts`), log in with `curl POST /auth/login`, test nominal and documented error cases one by one with `curl`, then clean up (delete the account and data, stop the server). Never repoint the front's `.env` for this.
- A change that **replaces** an existing write path must not be merged until the endpoint it depends on is confirmed deployed in prod.
- **A 401 without token does not prove a route is deployed** (API session, 2026-11-17): authentication runs before route matching on protected prefixes such as `/foods`, so an undeployed route also answers 401. Proof of a prod deployment = the migration applied in the prod database, an **authenticated** request to the route answering 200, and the new key present in an authenticated `/bootstrap` when relevant. Ask the API session for that confirmation.

## General

- Base URL: `VITE_API_URL` (see `docs/development.md`). Bearer access token; JSON.
- Error envelope: `{ "error": { "code", "message" } }`, French messages ready to display. Common codes: `VALIDATION_ERROR` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `CONFLICT` (409), `RATE_LIMITED` (429).
- Deleting an entity still referenced → **409 CONFLICT** (FK `Restrict`).
- CORS: exact origins `https://jduquenne.github.io` and `http://localhost:5173` (origin without the `/artemis-foodlab/` path), `credentials: true`, never `*`.
- Rate limits (prod): writes 300 / 15 min / IP (GET/HEAD/OPTIONS exempt; a batch counts once), import 20 / 15 min, login 10 failures / 15 min, `/media` 1000 / 15 min, `/media/resolve` 240 / 15 min.

## Auth and session

- `POST /auth/login`, `POST /auth/refresh`, `PUT /me/password` return `{ accessToken, refreshToken, user }`; the `refresh_token` cookie (`SameSite=None; Secure; HttpOnly; Path=/auth`) remains as a fallback. `POST /auth/refresh` and `POST /auth/logout` accept `{ refreshToken }` in the body (body wins over cookie). Refresh without cookie nor body → 401. Refresh tokens rotate on every use; replaying a rotated token → 401 "Session compromise" and purge of all the account's sessions (API side, 2026-09-30: a 15 s grace on replay was coded; its deployment was not confirmed at the time).
- Access-token TTL in prod: 30 days (`ACCESS_TOKEN_TTL_MINUTES=43200`); refresh-token TTL 30 days. The role is inside the JWT: a self-demoted admin keeps admin rights until the token expires.
- `AuthUser = { id, email, role: "admin" | "guest", freezerName, displayName: string | null }` — same shape in login / refresh / `GET /me` / `PUT /me` / `PUT /me/password`.
- `GET /me`. `PUT /me { freezerName?, displayName?, email? }` (≥ 1 field; email taken → 409; `{}` → 400).
- `PUT /me/password { currentPassword, newPassword }` → 200 `{ accessToken, user }` (session renewed, reuse the new token); wrong current password → **400** `VALIDATION_ERROR` ("Le mot de passe actuel est incorrect.", on purpose not 401); new password ≥ 12 chars; other sessions are logged out.
- `POST /auth/demo` → 201, same shape as login + `demoExpiresAt` (guest account with `isDemo`, pre-filled, purged after ~2 h). Errors: `DEMO_RATE_LIMIT` (429, 3/h/IP), `DEMO_CAPACITY` (503, 15 active / 50 per 24 h), `DEMO_FORBIDDEN` (403: catalogue writes, upload, `/users`, `/import`, password, e-mail). Refresh is capped at `demoExpiresAt`.

## Bootstrap

`GET /bootstrap` returns the whole boot pack in one response, each key identical to the shape of its standalone endpoint: catalogue (recipes, outdoor activities, foods, household items, recipe categories), household shopping flags (`flaggedAt`), profiles, journal overrides of all profiles, current shopping period, price stores and latest food prices (D-064). (`journalSettings` is no longer read.) Measured ~150 ms server, ~360 KB gzip.

## Catalogue reads

`GET /recipes` (all at once, no pagination), `GET /recipes/:uuid` (404 if absent or if the uuid is an outdoor activity), `GET /outdoor-activities`, `GET /foods`, `GET /household-items`, `GET /recipe-categories`, `GET /ingredient-categories`.

- Recipes carry `announcedAt` (ISO UTC `…Z` or `null`): set server-side by `POST /recipes`, untouched by `PUT`, `null` for seeded/imported recipes. A `PUT` cannot force it (to be requested if an admin "re-announce" toggle is ever needed).
- `assets.<key> = { url, key }` (`mealPhoto`, `bookPhoto`; `assets = {}` if none).

## Media

- `url` of an asset = always the `/media/<key>` redirect (stable, `Cache-Control: private, max-age=3600`) → 302 to a signed Supabase URL. **Never store the redirect target.** `GET /media/<key>`: 302, or 404 `NOT_FOUND` for an unknown/invalid key (404 = give up; anything else = retry).
- `POST /media/resolve { keys: string[] }` → 200 `{ urls: Record<key, signedUrl>, expiresAt }`. Unknown key → simply omitted. `keys: []` → 400; key with `../` → 400; > 200 keys → 400; no token → 401. `expiresAt` = one floor for the batch (`now + 6 d`, real signature 7 d).
- Hotlinking from `github.io` is fine. Using direct Supabase URLs in a canvas with `crossorigin` would require configuring the bucket CORS (tell the API); the front does not need it.

## Planning

- `PUT /planning-slots/:year/:week/:day/:slot` upserts a slot; `DELETE /planning-slots/:apiId`. `:day` free string (`monday`), `:slot` ∈ `breakfast|lunch|snack|dinner`.
- `POST /planning-slots/:slotId/items` accepts any plannable `itemId` (recipe or outdoor activity uuid); unknown → 400.
- **Batch** — `PUT /planning-slots/:id/items/batch`, body `{ add?: { itemId, isDessert?, personsOverride?, gramsOverride? }[], remove?: uuid[], update?: { id, isDessert?, personsOverride?, gramsOverride? }[] }`, at least one non-empty array; the same `id` cannot be in both `remove` and `update` (400). `position` on `add` is ignored (append server-side).
  - Response 200 `{ items: [{ id, itemId, isDessert, personsOverride, gramsOverride, position }] }` = **full, up-to-date state of the slot**, sorted by `position`. Rebuild the local cache from this whole array; never correlate by index with the `add` sent.
  - All or nothing: unknown catalogue `itemId` → 400; `id` unknown or outside the slot → 404; empty body → 400; unknown slot → 404. Positions are not renormalised after a `remove` (verified; no front impact).
  - Limit: scoped to one slot. A drag & drop uses the move route below (since v6.167.1).
- **Move / swap** (API D-074, issue #66; **live in prod**, API commit `fdb7e35`, 2026-11-25; a malformed body may still return a zod default English message until the next API push, same shape and status: never parse these messages): `POST /planning-slots/move { from: { year, week, day, slot }, to: {…}, mode: "move" | "swap", moveDesserts?: boolean (default false), keptDessertIds?: catalogue itemId[] }` (`keptDessertIds` only with `move` + `moveDesserts`; `day` « Lundi » … « Dimanche », week valid in the ISO year). One transaction, target slot created if missing. Moved items only change slot: id, `isDessert`, persons / grams overrides, `foodChoices`, `accompanimentChoices`, `baseVersionChoices` and journal overrides kept; frozen links untouched (nothing given back or taken); appended after the items staying in the slot (positions not compacted). `swap`: dishes exchanged (desserts too with `moveDesserts`), nothing deleted. `move`: source dishes go to the target, the target dishes are deleted when at least one dish moves; with `moveDesserts` the source desserts merge into the target (same itemId → the target row is kept), above 3 desserts `keptDessertIds` is required and every dessert of either slot not listed is deleted; without `moveDesserts` desserts stay. Deleted items give back their frozen links unless their slot day is past (D-073). The source slot is kept even when empty; `persons` stays with each slot. 200 `{ slots: [source, target], freezerBatches }` (slots = `GET /planning-slots` elements). Errors: 404 « Le créneau source est introuvable. »; 400 « Le créneau source ne contient aucun plat à déplacer. » (« … aucun repas à déplacer. » with `moveDesserts`), « Il n'y a rien à échanger entre ces deux créneaux. », « Le créneau cible aurait 4 desserts (3 au maximum) : envoyez keptDessertIds pour choisir ceux à garder. », « Le dessert "x" n'est ni dans le créneau source ni dans le créneau cible. »; zod 400 « Le créneau source et le créneau cible doivent être différents. », « Le mode doit être "move" ou "swap". », « Le jour doit être un jour de la semaine en français (Lundi à Dimanche). », « Cette semaine n'existe pas dans cette année ISO. », « keptDessertIds ne s'utilise qu'avec mode "move" et moveDesserts: true. », « keptDessertIds doit contenir au moins un dessert. ». Dev example: move from a past day holding a 350 g frozen link → 200, target item keeps `baseVersionChoices: [{ …, version: "frozen", freezerItemId, quantity: 350 }]`, `freezerBatches: []`, batch unchanged. Front: `moveMeal` (`planningService`), `buildMoveSlotsPayload` / `ApiMoveSlotsResponse` (`planningApiMapper.ts`), mode from `dragMoveMode`.
  - Front: `core/services/planningService.ts` (`saveSlot`) + `core/logic/planning/planningApiMapper.ts` (`buildSlotItemsBatchPayload`, `mapApiItemsToSlotFields`). No automatic fallback to one-by-one calls.
- **Bulk add dishes and desserts** (D-035; live in prod, confirmed by the owner on 2026-10-21) — `POST /planning-slots/bulk-items { entries: [{ year, week, day, slot, itemId, isDessert? }], onConflict: "skip" | "fail" }`, 1..200 entries (empty or > 200 → 400; was 100 before the 2026-10-17 extension), counts once in the write limiter. `day` must be a French day name (`Lundi`…`Dimanche`, stricter than `PUT /planning-slots/:year/:week/:day/:slot`); `slot` ∈ `breakfast|lunch|snack|dinner`; `year` / `week` = ISO week-year / week (week checked against the real number of ISO weeks: 2026-W53 ok, 2027-W53 → 400); `itemId` any catalogue item (recipe or outdoor; dish / meal type not checked).
  - Each written entry: slot created if absent (`persons: null`, an existing slot keeps its persons), item appended in body order with `isDessert` (default `false`), no overrides, `foodChoices: []`, position = max + 1.
  - Extension 2026-10-17 (backward compatible; real dev payloads received the same day: (a) dish + side + 2 desserts on an absent slot → one slot, items at positions 0-3 in body order, `skipped: []`; (b) a slot with a dish receiving dish + side + 1 dessert (skip) → both dishes in `skipped` with `slot_has_dish`, **the dessert is still written** after the existing dish; (c) a slot with 3 desserts + 1 more → `skipped` `dessert_limit`; fail variant with a valid entry on a new slot + `dessert_limit` + `dessert_exists` → 409 « Repas non planifiable(s) : 2026-W45 Mercredi lunch dessert … (le créneau a déjà 3 desserts) ; … (ce dessert est déjà dans le créneau). », the new slot not created; (d) exact duplicate → 400 « ✖ Un même repas ne peut figurer qu'une fois par créneau dans la demande. »; the « 5 dishes in one slot » 400 was not captured): the same slot may appear several times; an exact duplicate `(year, week, day, slot, itemId, isDessert)` → 400 (absent `isDessert` = `false`; the same item once as dish and once as dessert is allowed); per slot in the body: at most 4 dishes (« Au plus 4 plats par créneau. ») and 3 desserts (« Au plus 3 desserts par créneau. ») → 400 (only this route enforces them).
  - Dish entries: if the slot already holds a non-dessert item, **all** dish entries of that slot are skipped (`slot_has_dish`), one `skipped` element each. Dessert entries never depend on dishes: already in the slot as dessert → `dessert_exists` (not duplicated); slot already at 3 desserts (earlier accepted desserts of the same call included) → `dessert_limit`. `skip` → those entries left out, the rest written; `fail` → 409 `CONFLICT` as soon as any entry would be skipped (any reason), nothing written, each entry and its reason in the French message.
  - One transaction, target slots locked: a concurrent write on the same slot (any planning route) waits, no race on the conflict check.
  - 400 `VALIDATION_ERROR`, nothing written: unknown `itemId` (message lists the ids), invalid day / slot / week, an exact duplicate entry, more than 4 dishes or 3 desserts for one slot in the body, `onConflict` missing or unknown.
  - 200 `{ slots, skipped }`: `slots` = every touched slot **including the skipped ones** (current server state), same shape as a `GET /planning-slots?year=&week=` element, sorted year, week, Monday → Sunday, breakfast → dinner (do not rely on order); `skipped: [{ year, week, day, slot, itemId, isDessert, reason }]` (`reason` ∈ `slot_has_dish` | `dessert_limit` | `dessert_exists`; before the extension: `{ year, week, day, slot }` only), `[]` when none.
  - Not supported: persons, overrides, food choices, replacing or removing items.
  - Front: `planningService.bulkAddPlanningItems` + `planningApiMapper.buildBulkItemsPayload` (always `onConflict: "skip"`, dishes only so far, one per slot; counts `skipped.length` as skipped meals, still correct with dishes only), cache rebuilt with `mapApiSlotToMealSlot` on every returned slot. Desserts use the extension (`isDessert: true` entries, v6.119.0); automatic side dishes were dropped for now (owner, 2026-10-17).
- **Usage stats** — `GET /planning-slots/recipe-usage?slots=lunch,dinner` (`requireAuth`, caller's own planning only) → `{ items: [{ code, plannedCount, firstWeek, lastWeek }] }`. Only `plannedCount > 0`, recipes only; weeks as `"YYYY-Www"` zero-padded; sorted `plannedCount` desc then `code`; no pagination; unknown `slots` value → 400.

## Journal and profiles

- `POST /journal-overrides` **replaces all 3 fields** (`portionsOverride`, `gramsOverride`, `ingredientOverrides`) on every call — an omitted field is erased. Always send the current state of the three. Accepts `profileId` (absent → first profile). Overrides of an ingredient cascade when it disappears from its recipe; overrides of a slot item cascade when it is removed from the planning.
- `GET/POST/PUT/DELETE /profiles`: max 3 per account (409), deleting the last profile → 409. Profile = name (unique per account), color slug, position, 5 targets.

Lifecycle: the base ingredient loses its group → its choices are deleted; the ingredient is removed from the base → deleted (FK cascade); **the dish stops using the base → the choices are kept as orphans** in `GET /planning-slots` (they become valid again if the dish uses the base again), but resending one → 400 « … n'appartient pas à la recette planifiée. », `foodChoices: []` → 200. **Front rule: ignore choices whose ingredient is not reachable from the planned recipe and never resend them** (moves, copies, choice edits). `bulk-items`, `POST /import`, recipe category change and demo seeding neither read nor write choices; the 409 guard on deleting a default food covers bases too. Unchanged: journal ingredient overrides accept top-level ingredients only.

## Prices (API D-064, front D-043; live in prod 2026-11-14)

Source of truth for shapes and messages: the API repo `docs/spec-catalogue.md` § Food prices and stores.
- `GET /price-stores` (any signed-in account; sorted by name, city), `POST` (201), `PUT /:id` (full replacement), `DELETE /:id` (204; 409 « Ce magasin a des prix enregistrés et ne peut pas être supprimé. »): body `{ name, city }` (trimmed, 1 to 80), response `{ id, name, city, createdAt }`; 409 « Le magasin "X" à Y existe déjà. ». Writes admin only (demo 403 `DEMO_FORBIDDEN`).
- `POST /food-prices` (admin, 201): body `{ foodId, storeId, pricePerKg, recordedAt?, paidTotal?, purchasedGrams? }`; response `{ id, foodId, storeId, pricePerKg, recordedAt, paidTotal, purchasedGrams, recordedByUserId }`, numbers as numbers. `pricePerKg` > 0, ≤ 100000, **at most 4 decimals** (refused, never rounded: the front rounds); `paidTotal` 2 decimals and `purchasedGrams` 3 decimals, **both or neither**; `recordedAt` defaults to now, at most one day in the future. No `PUT`.

## Cooking sheets (API D-065, front D-044; live in prod 2026-11-17)

Source of truth: the API repo `docs/spec-catalogue.md` and D-065. Received from the API session on 2026-11-17 with real payloads (dev); deployment in prod confirmed by the API session the same day.
- Entry shape (every key always present, nulls sent as `null`, numbers as numbers): `{ foodId, method, minMinutes, maxMinutes, temperatureC, cookedRatio, note, updatedAt }`. `method` ∈ `oven, steam, air_fryer, boiled, pan, microwave, pressure_cooker, raw` (lists are sorted in this order). `updatedAt` = last PUT for that food, shared by all its sheets. Key = (food, method), no id.
- `GET /foods/:id/cookings` (any signed-in account, demo included): the food's sheets, `[]` when none. Not used by the front (the bootstrap carries everything).
- `PUT /foods/:id/cookings` (admin; guest 403 « Cette action est réservée aux administrateurs. », demo 403 `DEMO_FORBIDDEN`): body `{ cookings: [{ method, minMinutes, maxMinutes, temperatureC, cookedRatio, note }] }`, any order, a missing key counts as `null`, at most 8, `[]` clears. Full replacement in one transaction; 200 with the saved list (same shape and order as GET); a refused body leaves the stored sheets untouched. 404 « L'aliment "<id>" est introuvable. ».
- Rules: minutes whole 1 to 1440, `maxMinutes` needs `minMinutes` and is ≥ it (equal accepted); temperature whole 30 to 300 °C, oven and air_fryer only; ratio > 0, ≤ 10, at most 3 decimals (refused, never rounded); note trimmed, ≤ 120, blank → `null`; raw: note only; other methods: `minMinutes` or `cookedRatio` or both.
- 400 `VALIDATION_ERROR`, message « ✖ <text>\n  → at <path> » (one pair per problem; cross-field rules checked only once each field is valid on its own). Texts: « Les fiches de cuisson doivent être une liste. », « Un aliment ne peut pas avoir plus de 8 fiches de cuisson. », « Le mode de cuisson oven apparaît plusieurs fois. », « Le mode de cuisson doit être l'un de : … », « La durée minimale (or maximale) doit être un nombre entier de minutes. / doit être d'au moins 1 minute. / ne doit pas dépasser 1440 minutes. », « La durée maximale demande une durée minimale. », « La durée maximale doit être supérieure ou égale à la durée minimale. », « La température doit être un nombre entier de degrés Celsius. / doit être d'au moins 30 °C. / ne doit pas dépasser 300 °C. », « La température n'est acceptée que pour les modes oven et air_fryer. », « Le ratio cru → cuit doit être un nombre. / doit être strictement positif. / ne doit pas dépasser 10. / ne peut avoir que 3 décimales au maximum. », « La note doit être un texte. / La note ne doit pas dépasser 120 caractères. », « La fiche oven doit avoir au moins une durée ou un ratio cru → cuit. », « Le mode raw (cru) ne prend ni durée, ni température, ni ratio cru → cuit. ». The front validates first with the same texts (method names in French), so these should not show.
- `/bootstrap` `foodCookings`: top-level flat list next to `foods` and `foodPrices`, sorted by `foodId` then method order; a food without sheet has no entry. Measured on dev (390 foods, 414 KB gzip): ≈ 12 bytes gzip per sheet (+9.6 KB with 2 per food).
- Not available: single-sheet routes, history, a global `GET /food-cookings`, import. Deleting a food deletes its sheets.
