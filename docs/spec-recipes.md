# Spec — Recipes, recipe detail, news and Recipe Builder

## Catalogue browsing and search

- Catalogue by category, global search, macro filters (below).
- Scroll restoration (`shared/utils/scrollMemory.ts` module-level Map + `shared/hooks/useScrollRestore(key)` + `resolveRestoredCount` in `core/logic/recipe/recipeListLogic.ts`): on `CategoryDetail` (key `category:<id>`, also restores the infinite-scroll `visibleCount`, `fade-in-up` animation skipped on return) and on `RecipeSearchResults` (key `search:<query>:<filters>`). Not on the category list (owner's choice). Session memory only.
- Known limit: the global search only lists recipes with a meal photo (`mealPhoto`).

## Filters

Model `RecipeFilter { type: RecipeFilterType | null; macros: Partial<Record<kcal|proteins|lipids|carbohydrates|fibers, "below"|"above">>; inSeason: boolean; foodGroupId: string | null }` (`core/domain/recipeFilter.ts`), persisted in `localStorage` (`cipe_recipe_filter`, via `useMenuStore.recipeFilter`).

- Types (`FILTER_TYPE_DEFINITIONS`): Plats (`DISH` except categories `cereal-products`, `pastries`, `bases`), Petit déjeuner (`DISH` of `cereal-products`), Goûter (`DISH` of `pastries`). Bases/Ingredients types were removed (to reconfirm with the owner if needed).
- Threshold = **median per type** (`macroReferenceLogic.ts`, computed once per catalogue change via `useTypeMedians`), compared with per-portion macros (`RECIPE_MACROS`). « Moins » = `<` median, « Plus » = `>`. No type chosen → no macro filter.
- Season (v6.121.0): `inSeason` keeps the recipes in season for the **current month** (no choice of month or season, owner's request); the month is read at render time, so a saved filter follows the calendar. Rule = `isSeasonalRecipe` (§ Recipe season): at least one seasonal food, all of them in season this month; a recipe without any seasonal food (only all-year foods) is **hidden** (owner's choice B, 2026-10-21: choice A, the `isRecipeInSeason` rule of the generator, kept 729 recipes, far too many); « Surgelés » ingredients are not seasonal foods here (neither count nor block); only lunch / dinner dishes are kept (`RecipeKind.DISH`, not a dessert, meal type lunch or dinner; owner, 2026-10-21: no desserts, no bases, no ingredient recipes); in practice the seasonal foods are the fruits and vegetables (71 foods in prod on 2026-10-21, none elsewhere); the freezer content is not taken into account here (generator only). Independent from the type: active on its own, kept when the type is removed. Ids computed once per catalogue change by `useInSeasonRecipes` (`seasonalMealIds`) and passed to `filterRecipesByFilter`. Applies to the global search and to `CategoryDetail`. UI: « Saison » section on top of the modal (`SeasonFilterToggle`, with the count among the candidates), chip « De saison · octobre ».
- Food family (issue #36, v6.131.0, owner 2026-11-09: catalogue only, one family at a time, persisted with the other criteria): `RecipeFilter.foodGroupId` (D-033 family). `familyRecipeIndex(recipes, foods)` (`recipeFoodFilterLogic.ts`, one pass with `createFoodIndex`) maps each family to the **dishes** using at least one of its foods (direct ingredient, through bases recursively, or an « au choix » ingredient of that family); `useFamilyRecipeIndex` (`shared/hooks/`) memoises it; `filterRecipesByFilter` / `matchesRecipeFilter` take it (`inFamily`). It works with or without a type, and combines with season, type and macros. `RecipeFilterModal`: section « Famille d'aliments » (`FoodFamilyFilterSelector`, radio pills with the recipe count among the candidates, only families used by at least one dish, hidden when there is none), chip « Famille : Fromage » in `ActiveFilterChips` (« introuvable » if the family was deleted, the filter then matches nothing until removed). `normalizeRecipeFilter` keeps the family and falls back to `null` for a missing or invalid value (older saved filters stay valid, no migration); `setFilterType(null)` keeps season and family. Bases are not listed under a family filter (dishes only, like the food filter below).
- Food filter (issue #33, v6.130.0, `recipeFoodFilterLogic.ts`): `/recipes?food=<foodId>` (URL only, never persisted, `RECIPE_FOOD_PARAM`, `recipeFoodPath`) keeps the **dishes** (`RecipeKind.DISH`) using that food: `recipesUsingFood` reuses `recipeFoodIds` (direct ingredient, bases recursively, cycle-safe, and « au choix » group ingredients whose group contains the food), unlike the text search which only compares direct ingredient names. It forces the results view and **composes** with the text search and the type / macro / season filters (the filter modal count follows). `RecipeFoodFilterBanner` (« Recettes avec : Betterave rouge », cross = removes the param, all screen sizes, `ActiveFilterChips` stays hidden on mobile); the empty state says « Aucune recette avec « X » ne correspond à ces critères ». An unknown `food` id is ignored. The scroll key includes the food, and coming back from a recipe detail keeps the filter (it lives in the URL). Entry point: the freezer (`docs/spec-freezer.md`).
- UI: `RecipeFilterModal` (bottom sheet on mobile, centred modal from `sm:`), `FilterTypeSelector`, `MacroMedianRow`, `ActiveFilterChips`, `RecipeFilterButton`; live result count in the main button. Decision: D-020.

## Recipe detail and portions

`RecipeDetail` shows the SVG "recipe" card (`RecipeRecetteCard`, or `RecipeBookCard` if there is a book photo) with quantities scaled to a number of portions: `scaleRecipeToPortions(recipe, portions)` (`core/logic/recipe/recipeScalingLogic.ts`, linear `portions / defaultPortions`, rounded to 2 decimals, includes `baseId` ingredients — their quantity is a number of base portions, so proportional too). Need: cook a recipe written for ~2 for, say, 7 people without recomputing by hand.

- Portions come from `?portions=N` (`resolveInitialPortions`, falls back to the default if absent/invalid/≤ 0) or from the header `PortionsStepper` (min 1). State is **local**, not persisted, reset to the default when `recipeId` changes (previous/next chevrons build the URL without `portions`).
- Opening from the planning: see `docs/spec-planning.md`. Planning `persons` ≡ portions (`persons / defaultPortions`). Gram overrides (`recipeQuantities`) are not portions → ignored here.
- **Linked bases** (left column on `sm:`, row under the card on mobile, `LinkedBaseLink`, issue #34, v6.130.1): each base thumbnail opens the base's detail in a new tab **with the portions the parent needs**: `getLinkedBases(recipes, scaledRecipe)` returns `{ id, name, portions }` where `portions = basePortionsNeeded` = the scaled quantity of the `baseId` ingredients (a base ingredient quantity is a number of base portions, as in `macroLogic`), summed when the base appears several times, rounded to an integer, minimum 1 (the portions stepper is integer: half a base portion opens as 1). It follows the stepper because it reads the scaled recipe. Before, the link always opened the base at its default portions.
- **Macros are per portion, hence invariant under scaling**: `macros` and `handleEditInBuilder` use the **unscaled** recipe; only the card receives `scaledRecipe`.
- Limits: `RecipeMacroPage` (calculator, separate route `/recipes/detail/:id/macros`, editable per-ingredient quantities, not persisted) is not portion-aware and does not receive `?portions`; coming back from it resets portions to the default. For a recipe with only an instructions photo (no SVG card) the stepper shows but has no visual effect. `RecipeDetail` renders `null` if there is neither meal photo nor instructions photo.
- Unknown recipe id (stale link, deleted recipe): `RecipeDetail` and `RecipeMacroPage` show `RecipeNotFound` (« Recette introuvable », « Cette recette n'existe peut-être plus. », button back to `/recipes`). The calculator inputs are `DecimalInput`s (comma accepted, emptied field = 0). The filter modal does not close on a backdrop click.

## Cooked weight (D-041, planned, issue #51)

A dish may carry `cookedWeightGrams` (weight of the whole finished dish, > 0, null by default): the raw ingredients do not give the weight of the result (bread loses water). It lets a portion be expressed in grams without touching the macros (computed from the ingredients): factor = grams ÷ `cookedWeightGrams`. Recipe Builder field with the read-only weight per portion (`cookedWeightGrams ÷ defaultPortions`); recipe detail shows « 1 portion ≈ N g » and kcal per 100 g cooked; journal entry in grams: `docs/spec-journal.md`. Dishes only, planning and shopping stay in portions. **Status (v6.142.0): catalogue mapping and Recipe Builder field done ("Poids du plat cuit (g)" under « Portions par personne », dishes only, with the read-only weight per portion); journal entry in grams done (v6.143.0, `docs/spec-journal.md`); recipe detail done (v6.144.0: `CookedWeightInfo` under the macro circles, desktop column and mobile row, « 1 part ≈ N g cuits » and « N kcal / 100 g cuits » = `kcalPer100CookedGrams`, independent of the portions stepper); API on dev only, nothing to push before prod is confirmed.** Logic: `core/logic/recipe/cookedWeightLogic.ts` (`cookedWeightPerPortion`), `core/logic/recipeBuilder/cookedWeightLogic.ts` (validation > 0, ≤ 100000, 2 decimals; `cookedWeightToApi` always sends the value or `null`, `null` for a non-dish).

## Recipe season (D-034)

Derived client-side from the foods, never stored (`core/logic/season/recipeSeasonLogic.ts`, catalogue passed as `SeasonCatalogue { recipes, foods }`). `recipeSeasonalFoods` = the foods with a season (`Food.months` non-empty) used by the recipe, **bases included** (recursive through `baseId`, cycle-safe), deduplicated, sorted by name. A recipe is in season for a month when every one of them is (`isRecipeInSeason`, generator rule; a recipe without seasonal food is always in season); `isSeasonalRecipe` additionally requires at least one seasonal food (recipe filter rule); `outOfSeasonFoods` lists the culprits (for a « why » in the generator); `recipeSeasonMonths` = the months where it is in season (12 entries = all year, empty = never fully in season). An ingredient « au choix » counts with its recipe default; pass the recipe through `personalizeRecipe` first to use a profile's choice. Consumers: the weekly menu generator and the recipe filter « De saison » (§ Filters).

## News (« Nouveautés »)

Based on `announcedAt` (`docs/api.md` § Catalogue reads): `core/logic/news/newsLogic.ts` (`RECENT_RECIPE_DAYS = 30`, `getNewsGroups` → groups by local day, desc; recipes sorted by name; `latestNewsDate`). `useNewsStore` persists `lastSeenDate` only, `hasNew` is transient (`syncHasNew()` after hydration, bootstrap and builder save; `markAsSeen()`), and subscribes to catalogue changes. `NewsModal` navigates by `recipe.code`.

## Recipe Builder (admin only)

Access: `ChefHat` icon in `Layout.tsx` (admin), « Nouvelle recette » button of `RecipeModule`, pencil of `RecipeDetail`. Non-admins: route not mounted → redirected.

- **Header** = 3 buttons: Save (`SaveRecipePanel`), Load (`LoadRecipeModal`), New recipe (always asks for confirmation, then empties the whole form and the chosen photos).
- **Identity of the edited recipe**: `RecipeBuilderState.sourceCode` = code of the recipe loaded in the builder (`recipeToBuilderState`, set after a successful create), `null` for a new draft. `useBuilderSourceRecipe` returns that recipe when it exists in the catalogue. For an existing recipe the category and the N° (the code) are locked, the name stays editable, and Save always updates `sourceCode`. `validateBuilderIdentity` blocks a new draft whose code is already taken and a code change on an existing recipe (before 2026-10-08 changing the N° of a loaded recipe could overwrite another recipe). Changing the category of an existing recipe: see « Category change » below. Draft store version 4 (`migrateDraftV3ToV4` sets `sourceCode` to the draft's code).
- **Save**: confirmation recap (`summarizeBuilderState`), then `POST/PUT /recipes`, photo upload `POST /recipes/:id/photo`, then `syncRecipeFromApi(uuid)`; delete (confirmed with `ConfirmActionModal`, like the Dashboard) → 409 if referenced, then `removeRecipeFromCatalogue(code)`. The save modal does not close on a backdrop click. `validateBuilderState` requires at least one ingredient and a book page if `isFromBook`; `validateBuilderPhoto` requires a dish photo (newly chosen or already online) for **every** recipe type, ingredients included (owner, 2026-10-08); Save is disabled while errors remain. Existing recipes without a photo (Dashboard « Recettes sans photo ») can only be updated once a photo is chosen.
- **Variante** (header button, existing recipe only, `VariantModal`): asks for a new name (must differ from the source) and a dish photo, then turns the draft into a new recipe (`toVariantDraft`, `core/logic/recipeBuilder/recipeVariantLogic.ts`): `sourceCode` cleared, N° = next free number of the category, category editable again, ingredients copied without their API ids.
- **Ingredient ids are stable**: `recipeToBuilderState` keeps `ing.id` in `DraftIngredient.apiId` (distinct from `DraftIngredient.id`, the local/React key); `builderStateToApiBody` sends it back when present (`docs/api.md` § Catalogue writes).
- **Ingredient « au choix »** (D-033): a food ingredient linked to a food that belongs to a family shows a `Shuffle` toggle (`IngredientChoiceToggle`; full-width button in the mobile drawer, « Au choix » badge on the mobile card). On = `DraftIngredient.foodGroupId` set to the food's family (`toggleFoodChoice`); the linked food stays the **recipe default** (`foodId`). Picking another food keeps the choice only if it belongs to the same family (`applyFoodPick`, which now receives the picked `Food`); switching to « Base » clears it. An ingredient au choix is allowed in a recipe of kind `base` since v6.123.0 (D-037 step 1, API D-057; the former `validateBuilderState` refusal is removed). Sent as `foodGroupId` in `POST/PUT /recipes` (`null` otherwise). Display: « (au choix) » appended to the ingredient on the recipe cards (`formatNameWithNotes`, merged with the preparation), « au choix » next to the name in the nutrition calculator. Macros keep using the default food.
- **Meal types** (owner, 2026-10-16): a new draft starts with **no meal type checked** (`initialRecipeBuilderState`); at least one is mandatory for a non-base recipe (`validateBuilderState`: « Sélectionne au moins un type de repas. »). Before, lunch + dinner were pre-checked and most pastries / cereal products inherited them; a one-off per-recipe review was applied in prod on 2026-10-16 (API `import:recipe-meal-types`, 168 dishes; after it: breakfast 172, lunch 509, dinner 507, snack 176 of 685 dishes). « Variante » keeps the source's meal types.
- **Meal types vs dessert** (owner, 2026-10-16): `mealTypes` says **when the recipe is eaten as a meal**; `isDessert` alone says whether it can be added as a **dessert** to a lunch / dinner slot (manual add, `DessertPicker`). The two are independent: a fruit salad is `breakfast, snack` + `isDessert` and stays available as a dinner dessert. Savory bites for an apéritif are `snack` for now (apéritif category / slot: owner's decision pending).
- **Auto number**: `suggestNextRecipeNumber(categoryId)` = max number of existing codes with that prefix + 1, applied on category change if the recipe does not exist yet.
- **Category change of an existing recipe** (owner, 2026-10-10, v6.84.0): the locked category field is a button styled as disabled; **5 clicks within 3 s** (`registerUnlockClick` / `isCategoryUnlocked`, `core/logic/recipeBuilder/recipeCategoryChangeLogic.ts`), with no hint, open `CategoryChangeModal` (built on `ConfirmActionModal`): new category (« À définir » by default, `outdoor` and the current one excluded), recap `avant → après` of the category and the code, consequence text (extra warning for the demo hard-coded codes `char-041`, `char-047`, `pv-017`), « Confirmer » only (no text to retype). The new N° is the next free one of the new category (`planCategoryChange`). `useRecipeCategoryChange` (pending key `recipe-category-change`) calls `PATCH /recipes/:id/category` (only code + category; unsaved draft edits are not sent), then resyncs the whole catalogue (other recipes' `baseId` codes), patches the draft (`categoryId`, `recipeNumber`, `sourceCode`), resyncs the freezer and bumps `useRefreshStore` (planning, journal, shopping refetch).
- **Category « À définir »** (owner, 2026-10-10): a new draft and « Nouvelle recette » start with `categoryId: ""`; the select shows a disabled « À définir » option, the N° stays empty and disabled until a category is chosen, and Save is blocked by « La catégorie est obligatoire. ». « Variante » keeps the source category. Persisted drafts keep their category. The `outdoor` category (activities) is never offered (`isRecipeCategory`) and is rejected by `validateBuilderState` (v6.84.1).
- **Portions per person** (D-040 step 1, v6.140.0, issue #40): `RecipeDetails.portionsPerPerson?: number` (the reference number of recipe portions one person eats, 1 when absent: `portionsPerPersonOf`, `portionsPerPersonLogic.ts`). Recipe Builder: « Portions par personne » `DecimalInput` for **dishes only** (hidden for bases and ingredients), with a hint (« ex. 4 si la recette compte une portion par pancake et qu'on en mange 4 »); `RecipeBuilderState.portionsPerPerson?` (optional, so older persisted drafts stay valid; initial 1; loaded from the recipe; variants carry it). `builderStateToApiBody` always sends it (`portionsPerPersonToApi`: the value for a dish, 1 for any other kind or an empty value). `validatePortionsPerPerson` mirrors the API (> 0, ≤ 100, ≤ 2 decimals, floating noise tolerated) and is wired in `validateBuilderState`. **Effects** (step 2, v6.141.0, `core/logic/recipe/portionsPerPersonLogic.ts`: `portionsPerPersonOf`, `defaultPersonsOf`, `plannedPortions`): in `computeDishMacros` the default portion multiplier of a planned item is the reference (an explicit journal override replaces it, it does not multiply it); ingredient-kind recipes keep the gram logic; accompaniments stay per person (`portionOverrides ?? 1`). Hence the planning day kcal (`weekDayKcal`), the journal day totals and the week average count e.g. 4 portions of a pancake recipe per person. Persons shown for a planned recipe with no explicit persons (`defaultPersonsOf` = `defaultPortions ÷ reference`, e.g. 20 pancakes at 4 per person = 5 persons, which is the whole recipe, as before): `SingleMealSlot`, `MultiMealSlot` badge and persons editor. The recipe detail page opened from the planning gets `plannedPortions(persons, recipe)` = `persons × reference` (rounded, min 1; no parameter when persons is not set).
- **Industrial equivalent** (D-038 delivery A step 1, v6.133.0, issue #37): `RecipeDetails.industrialEquivalent?: { foodId, quantity, unit }` (quantity per portion of the base; mapped by `mapApiRecipe`, tolerant to the field being absent while the API is not deployed, `null` → `undefined`). Recipe Builder: for a `base` recipe, `IndustrialEquivalentField` (« Version industrielle », Ajouter / Retirer, `FoodSearchInput` to pick the store-bought food, quantity per portion of the base `DecimalInput`, unit select, the unit of the food preselected) under the options; the draft is `RecipeBuilderState.industrialEquivalent?: IndustrialEquivalentDraft | null` (optional so older persisted drafts stay valid, no store migration). `core/logic/recipeBuilder/industrialEquivalentLogic.ts`: `industrialDraftToApi` always returns an object for a complete draft of a base and **`null` otherwise** (so a clear, or a base turned into a dish, never trips the API `CHECK`), `validateIndustrialDraft` (« Version industrielle : choisis un aliment et une quantité supérieure à 0 par portion de la base. », only for a base with an incomplete draft, wired in `validateBuilderState`). **Creating the store-bought product on the spot** (v6.137.0, owner 2026-11-09: « un nom et une quantité »): `FoodSearchInput` takes an optional `onCreate`; when the typed text matches no food (`canCreateFoodFromQuery`: ≥ 2 characters, accent / case insensitive, no existing name) it adds « Créer "<nom>" » to the suggestions, which opens `FoodFormModal` with `initialDraft` = `industrialFoodCreationDraft(name)` (name, macros « 0 »), then the created food (`useCatalogueFoods().create`, catalogue resynced) is selected with its unit. A note says that without nutritional values the home version's kcal are kept. `FoodFormModal`, `FormModalShell`, `FormField` and `SeasonMonthsField` moved from `features/dashboard/` to `shared/components/ui/form/` (features do not import each other); the dashboard imports them from there. Loading a recipe in the builder (`recipeToBuilderState`) and variants carry it. Effects on the planning, shopping and macros come in the next steps.
- Default portions of a new recipe: **2** (`initialRecipeBuilderState`). A persisted draft (`cipe_recipe_builder`) keeps its value until « Nouvelle recette ».
- **Photos** (`components/photo/PhotoPanel.tsx`): preview, choose/replace (`PhotoField`), book photo if `isFromBook`. The `File`s live in `RecipeBuilderModule` state, passed to `PhotoPanel` and `SaveRecipePanel`.
- **Download** « Télécharger la recette »: generates the SVG recipe card from the **current builder state** (`builderStateToRecetteCardData` / `builderStateToBookCardData` in `shared/utils/cards/cardAdapter.ts`, book variant if `isFromBook` with a book photo), then rasterises it to PNG ×3 (`shared/utils/cards/cardExport.ts`; images converted to `data:` URLs to avoid a tainted canvas). It is **not** the raw dish photo.
- **Instructions**: `RecipeMetaForm` only has a button (first-step preview + « N étapes »); editing happens in `InstructionsModal`: one line = one step, fully controlled by `state.instructions: string[]`, `Enter` = next step, `Shift+Enter` = line break, ↑/↓, ✕, « Ajouter une étape ». A multi-line paste is split into steps (`splitPastedInstructionLines` / `spliceInstructionPaste`, `instructionsLogic.ts`), cut at the cursor; numbers/bullets in the pasted text are not stripped (deliberate).
- **Macro preview** (`MacroPreview`): one compact tile per macro + kcal, toggle Portion / Total ×N, note « N sans données ».
- **Layout**: desktop `lg:` locked bento (left column Photo + metadata, right column thin macro bar + full-height ingredients). Mobile (< `lg`): single page scroll, sticky header, stacked cards; ingredient rows use `IngredientMobileCard` + `IngredientEditDrawer` (bottom sheet).
- A free-text preparation already in the database (outside `PREPARATION_OPTIONS`) shows empty in the `<select>` (known).
